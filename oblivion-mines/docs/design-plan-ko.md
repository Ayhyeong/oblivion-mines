# 망각의 지뢰 — 웹 구현 기획안

> 11×11 보드 위에서 두 플레이어가 서로의 지뢰 배치를 모르는 채 이동하며 점수를 겨루는 비대칭 정보 게임의 웹 구현 설계서.

---

## 1. 개요

### 1.1 게임 한 줄 요약

각자 15개의 지뢰를 비밀리에 깔고, 상대 지뢰의 위치를 추론하면서 보드를 걸어 점수를 모으는 2인 턴제 게임. 세 개의 보물이 모두 회수되면 즉시 끝난다.

### 1.2 이 게임이 웹 구현에서 어려운 이유

일반적인 보드게임과 달리 **양측이 서로 다른 정보를 본다.** 체스나 바둑은 클라이언트가 전체 상태를 알아도 되지만, 이 게임은 상대의 지뢰 15칸이 클라이언트 메모리에 들어오는 순간 게임이 끝난다. 따라서 다음 세 가지가 설계의 중심이 된다.

1. **정보 격벽** — 클라이언트는 상대 지뢰를 어떤 경로로도 받지 않는다.
2. **판정의 결정성** — 점수 계산은 단일 순수 함수로 고정하고, 종료 후 재현 검증이 가능해야 한다.
3. **추론 지원** — 점수는 공개 정보이므로, 그로부터 상대 지뢰를 역산하는 것이 이 게임의 핵심이다.

### 1.3 범위

| 포함 | 제외 |
|---|---|
| 1:1 대전 | 3인 이상 |
| 온라인 연결 | 오프라인 진행 |
| 사람간 대전 | AI 상대 |
| 리플레이 및 검증 | 토너먼트 운영 도구 |
| 게스트 플레이 | 레이팅/점수 |

## 2. 규칙 명세 (정규화)

### 2.1 좌표계

- 열: 왼쪽→오른쪽 `a`~`k` (0~10)
- 행: 아래→위 `1`~`11` (0~10)
- 내부 인덱스: `idx = row * 11 + col`, 범위 `0~120`
- 인접: 8방향(체스 킹 이동)

### 2.2 시작점과 금지 칸

| 구분 | 칸 |
|---|---|
| 白 시작 구역 | `a1` `a2` `b1` `b2` |
| 黑 시작 구역 | `k11` `k10` `j11` `j10` |
| 보물 | `a11` `f6` `k1` |

위 11칸에는 **양측 모두** 지뢰를 설치할 수 없다. 배치 가능 칸은 110개.

흥미로운 기하학적 사실: 세 보물은 `col + row = 10` 안티대각선 위에 정확히 놓여 있고, 이 선이 보드를 55:55로 양분한다. 즉 보물은 전부 중립 지대에 있다.

### 2.3 배치 단계

- 각자 정확히 15칸을 선택. 같은 칸 중복 불가.
- 양측이 **동시에, 서로 모르게** 제출.
- 서로 다른 플레이어가 같은 칸을 골라 한 칸에 지뢰 2개가 놓이는 것은 허용된다.
- 양측 제출이 완료되면 플레이 단계로 전이.

### 2.4 이동

- 게임 시작은 白 a1, 黑 k11에서 시작한다.
- 白 선공, 이후 번갈아 1수씩.
- 인접 8칸 중 하나로 이동. 보드 밖 불가.
- **상대 말이 있는 칸으로는 이동할 수 없다.**
- 지뢰를 밟으면 점수 계산 후 즉시 자기 시작 구역 4칸 중 **본인이 선택한** 한 칸으로 복귀한다. 그 칸에 상대 말이 있으면 그 칸은 선택지에서 제외된다. 시작 구역으로 이동이 완료된 후 상대 차례로 넘어간다.

### 2.5 점수

우선순위 순으로 판정한다.

1. **지뢰 있음** → `-5`점. 그 칸의 지뢰는 양측 것 모두 즉시 소멸. 시작 구역으로 복귀(복귀 칸에서는 점수 가감 없음).
2. **미획득 보물 칸** → 획득 순서에 따라 `+10 / +15 / +20`. 보물은 소멸. **인접 지뢰 점수는 계산하지 않는다.**
3. **이미 밟은 칸** (양측 통합 기준) → `0`점.
4. **신규 칸** → 인접 8칸에 존재하는 지뢰의 **총 개수**(양측 합산, 한 칸 2개면 2로 계상)만큼 획득.

> 자기 지뢰도 밟으면 동일하게 `-5`이며, 자기 지뢰도 인접 점수에 포함된다. 이 두 조항이 게임 전략의 축을 만든다(§10 참조).

### 2.6 종료

- 세 보물이 모두 회수되면 즉시 종료.
- 무한 지연 방지를 위한 **수 상한: 각자 60수**. 도달 시 점수 우위로 판정, 동점이면 무승부.
- 기권 / 상대의 마지막 수 이후 일정 시간 초과 시 상대 승.

### 2.7 엣지 케이스 재정표

실제 대국에서 실제로 문제가 되었던 항목들이다. 구현 시 이 표가 테스트 케이스가 된다.

| # | 상황 | 재정 | 근거 |
|---|---|---|---|
| E1 | 시작 칸 `a1` / `k11` | 이미 밟은 칸으로 초기화 | 첫 복귀 시 점수 획득 방지 |
| E2 | 한 칸에 지뢰 2개 | `-5` **1회**, 2개 모두 소멸 | 페널티 중첩 없음 |
| E3 | 자기 지뢰 | 동일하게 `-5` | 규칙에 예외 없음 |
| E4 | 복귀 칸의 점수 | 항상 0, 방문 처리 | 복귀는 이동이 아님 |
| E5 | 복귀 칸에 상대 말 | 해당 칸 선택 불가 | 동일 칸 점유 금지 |
| E6 | 보물 칸의 인접 지뢰 | 계산하지 않음 | 보물 점수로 대체 |
| E7 | 회수된 보물 칸 재방문 | 0점 (방문 칸 규칙) | — |
| E8 | 폭발로 소멸한 지뢰 | 이후 모든 인접 계산에서 제외 | 계산은 **착지 시점** 상태 기준 |
| E9 | 합법 수 부재 | 발생 불가(최소 2수 보장) | 코너 인접 3칸, 상대 말 최대 1칸 점유 |
| E10 | 보물을 서로 안 먹고 대치 | 수 상한으로 강제 종료 | §2.6 |

E8은 특히 중요하다. 점수는 착지하는 순간의 지뢰 배치로 계산되므로, 나중에 폭발이 일어나도 **과거 점수는 소급 변경되지 않는다.** 추론 보조 기능(§9.4)은 이 시간 축을 반드시 반영해야 한다.

## 3. 아키텍처

### 3.1 규칙 코어 분리

`packages/rules`를 **의존성 없는 순수 TypeScript 패키지**로 분리한다.

- 서버: 권위 판정에 사용
- 클라이언트: 합법 수 하이라이트, 낙관적 UI 반영에 사용 (지뢰 정보 없이 동작 가능한 부분만)
- 검증기: 종료 후 리플레이 재현에 사용

동일 코드가 다수의 곳에서 돌기 때문에 판정 불일치가 구조적으로 발생하지 않는다. 사람이 손으로 점수를 세다가 인접 지뢰 하나를 빠뜨리는 종류의 사고가 원천 차단된다.

## 4. 데이터 모델

### 4.1 서버 상태

전체 지뢰 위치, 각 플레이어 현재 위치, 이미 밟은 칸(두 플레이어 모두), 보물 위치 및 획득 여부

### 4.2 클라이언트 뷰

지뢰 설치 당시에는 본인의 것만.
설치 완료 후 본게임 시작 시 본인이 설치한 지뢰를 포함하여 모든 지뢰를 표기하지 않는다.
각 플레이어의 말은 두 플레이어 모두가 볼 수 있음.
각 플레이어는 '지뢰 의심 지역'을 각각 입력할 수 있으며, 이는 클라이언트 뷰 내에서 처리하므로 오직 본인만 볼 수 있다.

핵심은 `ClientView`에 상대 지뢰를 표현할 필드가 **타입 수준에서 존재하지 않는다**는 것이다. 실수로 흘릴 통로 자체를 없앤다.

### 4.3 직렬화 주의

`ServerState`를 그대로 `JSON.stringify` 해서 보내는 코드가 한 줄이라도 생기면 게임이 끝난다. 다음을 강제한다.

- `ServerState` → `ClientView` 변환은 `toClientView(state, side)` **단일 함수**로만 수행
- 소켓 송신 레이어는 `ClientView` 타입만 받도록 제한
- CI에 페이로드 검사 테스트 추가 (§14)

## 5. 상태 기계

```
   [lobby]
      │ 양측 입장
      ▼
 [placement] ──── 타임아웃(120s) ───→ 랜덤 배치 자동 제출
      │ 양측 제출 완료
      ▼
    [play] ◄──────────────┐
      │                   │
      │ 지뢰 폭발            │ 복귀 칸 선택
      ▼                   │
 [awaitReturn] ───────────┘
      │
      │ 보물 3개 소진 / 수 상한 / 기권
      ▼
  [finished] → 배치 리빌 → 검증 → 기록 저장
```

`awaitReturn`을 별도 상태로 둔 이유: 복귀 칸 선택은 플레이어의 선택이지 자동 처리가 아니다. 이 선택을 이동과 같은 턴 안에서 처리하면 네트워크 왕복이 꼬인다.

## 6. 핵심 알고리즘

아래의 모든 코드는 예시이다. 적절히 수정·보강하라.

### 6.1 이동 해결

```ts
function applyMove(s: ServerState, side: Side, to: Cell): MoveResult {
  const from = s.pos[side];
  const opp: Side = side === 'W' ? 'B' : 'W';

  // --- 검증 ---
  assert(s.phase === 'play' && s.turn === side);
  assert(neighbors(from).includes(to));
  assert(to !== s.pos[opp]);

  const mineCount = (s.mines.W.has(to) ? 1 : 0) + (s.mines.B.has(to) ? 1 : 0);

  // --- 1. 지뢰 ---
  if (mineCount > 0) {
    s.score[side] -= 5;
    s.mines.W.delete(to);
    s.mines.B.delete(to);
    s.detonated.add(to);
    s.visited.add(to);
    s.phase = 'awaitReturn';
    s.awaitReturnBy = side;
    return { kind: 'mine', delta: -5 };
  }

  // --- 2. 보물 ---
  if (TREASURES.includes(to) && !s.treasureOrder.includes(to)) {
    const award = [10, 15, 20][s.treasureOrder.length];
    s.score[side] += award;
    s.treasureOrder.push(to);
    commit(s, side, to);
    if (s.treasureOrder.length === 3) s.phase = 'finished';
    return { kind: 'treasure', delta: award };
  }

  // --- 3. 기방문 ---
  if (s.visited.has(to)) {
    commit(s, side, to);
    return { kind: 'visited', delta: 0 };
  }

  // --- 4. 신규 ---
  const gain = neighbors(to).reduce(
    (n, c) => n + (s.mines.W.has(c) ? 1 : 0) + (s.mines.B.has(c) ? 1 : 0), 0);
  s.score[side] += gain;
  commit(s, side, to);
  return { kind: 'fresh', delta: gain };
}
```

`neighbors()`는 121칸 전체에 대해 기동 시 한 번 전개해 `Cell[][]`로 캐싱한다. 경계 처리를 매번 하지 않는다.

### 6.2 복귀 처리

```ts
function applyReturn(s: ServerState, side: Side, cell: Cell) {
  assert(s.phase === 'awaitReturn' && s.awaitReturnBy === side);
  assert(HOME[side].includes(cell));
  assert(cell !== s.pos[side === 'W' ? 'B' : 'W']);

  s.pos[side] = cell;
  s.visited.add(cell);          // 점수는 주지 않음
  s.phase = 'play';
  s.awaitReturnBy = null;
  s.turn = side === 'W' ? 'B' : 'W';
}
```

## 7. 부정행위 방지

### 7.1 계층 구조

| 계층 | 방어 대상 | 수단 |
|---|---|---|
| L1 | 클라이언트 메모리 덤프 | 상대 지뢰를 애초에 보내지 않음 |
| L2 | 서버 조작 / 배치 사후 변경 | 커밋-리빌 |
| L3 | 판정 오류 | 종료 후 리플레이 재현 검증 |
| L4 | 사이드 채널 | 응답 크기 고정, 지연 정규화 |
| L5 | 다중 계정 / 관전 공모 | 대국 중 관전 비공개, 레이팅 이상 탐지 |

### 7.2 커밋-리빌

배치 시점:

```
salt   = crypto.getRandomValues(32 bytes)
digest = SHA-256( salt ‖ cells.sort().join(',') )
```

클라이언트가 `digest`를 계산해 서버에 `{cells, salt, digest}`를 보내고, 서버는 재계산으로 일치를 확인한 뒤 **`digest`만 상대에게 공개**한다. 종료 시 양측의 `{cells, salt}`를 공개하면 상대가 해시를 직접 검증할 수 있다.

이것이 막는 것: 서버(또는 서버를 운영하는 쪽)가 대국 도중 지뢰를 옮기는 행위. 막지 못하는 것: 서버가 상대 지뢰를 제3자에게 유출하는 행위 — 이는 신뢰 모델의 한계이며, 완전 무신뢰 구현은 ZK 증명이 필요하다. MVP 범위 밖으로 둔다.

### 7.3 리플레이 검증

종료 후 클라이언트는 `{양측 배치, 전체 로그}`를 받아 규칙 코어로 처음부터 재실행하고, 매 수의 `delta`와 최종 점수가 서버 기록과 일치하는지 확인한다. 불일치 시 경고 배너를 띄우고 신고 경로를 제공한다.

실제 대국에서 인간/외부 심판이 판정할 때 **한 칸에 지뢰가 2개인 경우를 1개로 세는 오류**가 발생한 사례가 있다. 이 계층은 그런 유형의 오심을 사후에 100% 검출한다.

### 7.4 사이드 채널

- 모든 `move_result` 페이로드를 고정 길이로 패딩
- 지뢰 여부에 따른 서버 처리 시간 차이를 없애기 위해 응답을 최소 지연(예: 80ms)으로 정규화
- 과잉 대응으로 보일 수 있으나, `delta` 계산 경로가 분기하는 이상 타이밍 누출은 실재한다

## 8. 네트워크 프로토콜

WebSocket, JSON 메시지. 모든 스키마는 `zod`로 정의하고 양쪽에서 공유한다.

### 8.1 클라이언트 → 서버

| 이벤트 | 페이로드 | 비고 |
|---|---|---|
| `join` | `{gameId, token}` | 재접속 포함 |
| `placeMines` | `{cells: Cell[15], salt, digest}` | 서버가 재계산 검증 |
| `move` | `{to: Cell, ply}` | `ply`로 중복/순서 방어 |
| `chooseReturn` | `{cell: Cell, ply}` | |
| `resign` | `{}` | |

### 8.2 서버 → 클라이언트

| 이벤트 | 페이로드 | 비고 |
|---|---|---|
| `view` | `ClientView` | 전체 동기화, 재접속 시 |
| `placementAck` | `{oppCommit?}` | 상대 제출 완료 알림 |
| `moveResult` | `MoveRecord` | 양측에 동일 내용 브로드캐스트 |
| `awaitReturn` | `{side, options: Cell[]}` | |
| `gameOver` | `{reason, score, reveal: {W, B}}` | 리빌 포함 |
| `error` | `{code, message}` | |

`moveResult`의 `delta`는 양측 모두에게 전달된다. 점수는 공개 정보이므로 필연적이며, 이것이 상대의 인접 지뢰 수를 역산할 단서가 된다. **정보전은 양방향이다.**

- 클릭으로 지뢰 토글, 우측에 `15 / 15` 카운터
- 금지 칸 11개는 시각적으로 비활성 + 호버 시 사유 표시
- **경로 경고**: 자기 시작 구역에서 세 보물까지의 최단 경로를 점선으로 겹쳐 보여주고, 그 경로 위에 자기 지뢰를 놓으면 경고 아이콘을 띄운다. (§10.4에서 설명할 실패 유형의 직접적 예방책)
- 프리셋: `무작위`, `대각 회랑`, `직선 벽`, `초기화`
- 제출 후 취소 불가 — 확인 모달 필수

## 10. 밸런스 분석 및 조정안

실제 대국 1판의 전수 분석에서 도출한 항목들이다. 표본이 1이므로 모두 **가설**이며, 텔레메트리로 검증한 뒤 적용해야 한다.

### 10.1 선공 이점

`a1 → f6`은 대각선 5수, `k11 → f6`도 5수다. 완전 대칭이지만 白이 먼저 두므로 **중앙 보물은 구조적으로 白의 것**이다. 첫 보물 10점 + 진입 과정의 필드 점수가 선공에게 확정적으로 주어진다.

조정 후보:

- **덤(코미)**: 후공에게 고정 `+5`점. 가장 단순하며 바둑에서 검증된 방식.
- **입찰**: 배치 제출 전에 양측이 "내가 선공을 잡되 상대에게 N점을 주겠다"를 비공개 입찰. 덤 값을 플레이어가 결정하므로 튜닝 부담이 없다.
- 실측 승률이 55% 미만이면 손대지 않는다.


### 10.2 보물 순서 역설

`10 / 15 / 20`은 **뒤에 먹을수록 이득**인 증가 구조다. 그리고 세 번째 보물을 먹는 쪽이 게임을 끝낸다. 여기서 비직관적인 결과가 나온다.

> 상대의 보물 진입로를 지뢰로 막아 성공하면, 상대가 늦어지는 대신 **내가 두 번째(15점)를 먹고 상대가 세 번째(20점)를 먹게 된다.** 차단이 상대에게 5점을 헌납한다.

실측 사례: `-5`점을 먹인 차단 지뢰 하나가, 보물 순서 역전으로 상대에게 **순 +10점**을 안겼다. 지연된 9수 동안 상대가 추가로 벌어들인 필드 점수까지 합하면 더 커진다.

이것은 잘 설계된 긴장 구조일 수도 있다. 다만 **플레이어가 이 구조를 모르면 그냥 함정**이다. 대응:

- 튜토리얼에서 명시적으로 설명
- 화면 상단에 보물 순서에 따른 점수를 상시 표시

### 10.3 자기 지뢰 문제

규칙상 자기 지뢰도 밟으면 `-5`다. 실제 대국에서 **자기 지뢰로 자기 진출로를 막아놓고 3수 만에 자폭한 사례**가 나왔고, 그 한 수가 승부를 갈랐다.

- `-5`점
- 복귀로 인한 템포 2수 손실
- 그 자리에서 얻을 수 있었던 `+6` 상실

단일 실수의 실질 손실이 **11점 + 템포 2수**였고 최종 점수 차는 3점이었다.

다만, 이 지점이 해당 게임의 가장 큰 특징이므로 이는 수정하지 않는다.

각 플레이어는 상대 지뢰는 물론이고, 자신의 지뢰마저 볼 수 없다. 오직 기억에 의존해야 한다.

### 10.4 룰셋 정의

```ts
interface Ruleset {
  id: string;
  mineCount: number;            // 기본 15
  treasureAwards: number[];     // 기본 [10, 15, 20]
  countOwnMines: boolean;       // 기본 true (false = 추론 모드)
  minePenalty: number;          // 기본 -5
  plyLimit: number;             // 기본 60
  komi: number;                 // 후공 보정, 기본 0
  showOwnMines: boolean;        // 기본 true (false = 망각 모드)
}
```

모든 대국 기록에 `rulesetId`를 함께 저장해 버전 간 통계를 섞지 않는다.
